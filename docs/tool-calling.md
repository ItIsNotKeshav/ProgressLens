# Tool Calling

ProgressLens implements its own tool-calling protocol in Rust, without relying on
a model-native function-calling API. The design gives full control over argument
validation and SQL generation, which is essential for security.

---

## Protocol Overview

The LLM is constrained to produce exactly one of two JSON shapes per response:

```json
// Request a tool
{
  "type": "tool_call",
  "tool": "filter_students_by_field",
  "arguments": {
    "conditions": [
      { "field": "section", "operator": "equals", "value": "A" }
    ],
    "limit": 25
  },
  "plan": "Filter students in section A from the current snapshot."
}

// Provide a final answer
{
  "type": "final_response",
  "message": "Found 42 students in Section A."
}
```

The `plan` field is required on every `tool_call`. It acts as chain-of-thought that
improves argument quality and makes agent reasoning transparent in logs.

---

## Parsing

The response is parsed with `serde_json` into a tagged enum:

```rust
#[derive(Deserialize)]
#[serde(tag = "type", rename_all = "snake_case")]
enum ModelDirective {
    ToolCall { tool: String, #[serde(default)] arguments: Value },
    FinalResponse { message: String },
}
```

If parsing fails (the model output markdown, reasoning text, or invalid JSON), the agent
injects a correction prompt and retries once:

```
"Your response was invalid. Return exactly one JSON object matching tool_call or
final_response, with no markdown or reasoning."
```

A second failure is a hard error — the iteration exits with `AI_INVALID_JSON`.

---

## Tool Dispatch

Tool names are matched against a fixed list in Rust. Unknown names return
`AI_TOOL_INVALID` without touching the database:

```rust
pub async fn execute(db, conversation_id, sheet_id, snapshot_id, tool, arguments) {
    match tool {
        "get_student_history"      => student_history(db, sheet_id, arguments).await,
        "compare_student_snapshots"=> compare_student(db, sheet_id, arguments).await,
        "find_declining_students"  => score_changes(db, sheet_id, arguments, false).await,
        "find_improving_students"  => score_changes(db, sheet_id, arguments, true).await,
        "search_students"          => search_students(db, sheet_id, arguments).await,
        "get_dashboard_metrics"    => dashboard_metrics(db, sheet_id, snapshot_id).await,
        "create_pending_operation" => create_pending_operation(db, ..., arguments).await,
        "filter_students_by_field" => filter_students_by_field(db, sheet_id, snapshot_id, arguments).await,
        _ => Err(format!("AI_TOOL_INVALID: Unknown tool '{tool}'.")),
    }
}
```

## Argument Validation Helpers

Two utility functions validate all numeric and string arguments before any SQL:

```rust
// Validates string: non-empty, within max_len. Returns owned String.
fn required_string(args: &Value, key: &str, max_len: usize) -> Result<String, String>

// Validates integer: present or uses default, within [min, max].
fn int_arg(args: &Value, key: &str, default: i64, min: i64, max: i64) -> Result<i64, String>
```

These are called at the top of every tool function before any database access.

## SQL Injection Prevention

### Parameterized Queries

All queries use SQLx bound parameters (`?`). No string is interpolated into SQL:

```rust
// Correct — value is a bound parameter
sqlx::query_as("SELECT ... WHERE lower(s.name) LIKE ? ESCAPE '\\'")
    .bind(&pattern)
    .fetch_all(db)

// There is no code like this anywhere in the codebase:
// format!("SELECT ... WHERE name = '{user_input}'")  ← would be vulnerable
```

### `filter_students_by_field` — Closed Operator Enum

This is the most complex tool because it generates dynamic `WHERE` clauses based on
model-provided conditions. The defense is a closed Rust enum:

```rust
enum FilterOperator {
    Equals, NotEquals,
    GreaterThan, LessThan, GreaterEqual, LessEqual,
    Contains,
    IsEmpty, IsNotEmpty,
}
```

The model sends a string like `"greater_than"`. Rust maps it to `FilterOperator::GreaterThan`.
Rust then generates the SQL fragment from a method owned by the enum:

```rust
fn sql_fragment(&self, alias: &str) -> String {
    match self {
        Self::GreaterThan => format!("CAST({alias}.value AS REAL) > CAST(? AS REAL)"),
        Self::Contains    => format!("lower({alias}.value) LIKE ? ESCAPE '\\'"),
        Self::IsEmpty     => format!("trim({alias}.value) = ''"),
        // ...
    }
}
```

**The LLM never produces SQL syntax.** It only selects an operator name from a predefined list.
The SQL fragment is always generated by Rust code, never by string-interpolating model output.

### Field Key Validation

When the model provides a `field` key for `filter_students_by_field`, Rust looks it up
in the database before generating the join:

```rust
let field_row = sqlx::query_as(
    "SELECT id, data_type FROM fields WHERE sheet_id = ? AND sheet_key = ?"
)
.bind(sheet_id).bind(&field_key)
.fetch_optional(db).await?;

let (field_id, data_type) = field_row.ok_or("AI_TOOL_ARGUMENT: Field not found")?;
```

If the model invents a field key that doesn't exist in the database, the query fails
safely with an error — it cannot create an unknown join or access data outside the
selected sheet.

### Numeric Operator Validation

If the model uses a numeric operator (`greater_than`, `less_than`, etc.) on a
non-numeric field, Rust returns an error before the query runs:

```rust
if operator.requires_numeric() && data_type != "score" && data_type != "level" {
    return Err(format!(
        "AI_TOOL_ARGUMENT: Numeric operator '{}' cannot be used on field '{}' of type '{}'.",
        op_str, field_key, data_type
    ));
}
```

### `LIKE` Wildcard Escaping

For `Contains` operator, user-provided values are escaped before being used in a `LIKE` pattern:

```rust
fn escape_like(value: &str) -> String {
    value
        .replace('\\', "\\\\")  // escape the escape character first
        .replace('%',  "\\%")   // escape LIKE wildcard
        .replace('_',  "\\_")   // escape LIKE single-char wildcard
}
```

The query uses `ESCAPE '\\'` to declare the escape character, and SQLx binds the
escaped pattern as a parameter.

## Dynamic Query Construction for Multi-Condition Filters

`filter_students_by_field` builds a query dynamically using one `JOIN` per condition:

```sql
SELECT DISTINCT s.id, s.name, s.roll_number
FROM students s
JOIN student_values sv0
  ON sv0.student_id = s.id
 AND sv0.snapshot_id = ?           -- bound: snapshot_id
 AND sv0.field_id    = ?           -- bound: field_id for condition[0]
 AND CAST(sv0.value AS REAL) > CAST(? AS REAL)  -- bound: "50"
JOIN student_values sv1
  ON sv1.student_id = s.id
 AND sv1.snapshot_id = ?           -- bound: snapshot_id
 AND sv1.field_id    = ?           -- bound: field_id for condition[1]
 AND lower(sv1.value) = lower(?)   -- bound: "A"
LIMIT ?                            -- bound: limit
```

- Each condition adds exactly one `JOIN` block
- All identifiers (`sv0`, `sv1`, etc.) are controlled by Rust loop indices, not model output
- All comparison values are bound parameters
- Up to 8 conditions are allowed (capped by Rust, not the model)

The bind list is built as a `Vec<SqlBind>` and applied in order:

```rust
enum SqlBind { Int(i64), Text(String) }
```

This avoids unsafe trait objects or `Box<dyn Trait>` while supporting heterogeneous bind types.

## Tool Result Formatting

Raw JSON from the database is not passed back to the model. Instead, `summarize_tool_result()`
formats each tool's output as human-readable text:

```
Student: Rahul Kumar (Roll: CS101)
  Snapshot #47 (2024-03-01): Coding Score: 78, Soft Skill: 3
  Snapshot #46 (2024-02-01): Coding Score: 72, Soft Skill: 3
  Snapshot #45 (2024-01-01): Coding Score: 68, Soft Skill: 2
```

This reduces token usage compared to raw JSON (no field names repeated for every value),
makes it harder for injected content in field values to look like instructions, and
produces more reliable model reasoning.

At most 10 items are shown per list — enough for complete answers without runaway token usage.

---

## Conversation History Compression

Prior tool results stored in `agent_messages` are compressed to one-line summaries before
being re-injected into the context:

```
[Prior turn tool result] Called search_students — 2 students matched the search
[Prior turn tool result] Called get_student_history — history for Rahul Kumar — 3 snapshots returned
```

Full results are not re-injected, which keeps the context window from filling up across
long multi-turn conversations.

## Adding a New Tool

To add a new tool to the agent:

1. **Define** a `ToolDefinition` in `agent_tools::definitions()` with name, description,
   `arguments_schema`, and `output_schema` JSON Schema objects

2. **Implement** the tool as an `async fn` returning `Result<ToolExecution, String>`
   with argument validation at the top

3. **Register** the tool in `agent_tools::execute()` by adding a `match` arm

4. **Format** the result in `agent::summarize_tool_result()` to produce human-readable output

5. **Compress** the history summary in `agent::brief_tool_summary()` for prior-turn recall

6. **Update** the system prompt's tool selection guide so the model knows when to use it
